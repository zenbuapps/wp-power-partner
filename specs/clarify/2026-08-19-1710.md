## Idea

> 目前新架構開站，都沒有計算費用
>
> 任務：
> 1. 每天一次，時間在 UTC+8 的凌晨5點，會發送 API 給 cloud.luke.cafe
> 會提供
>
> partner_id - (int) 該經銷商在 cloud.luke.cafe 網站上的 user_id
> cloud_user_id - (string) 該經銷商在 cloud.wpsite.pro 新架構網站上的 user_id
> sites - (array) site array, 包含 domain, status, dailyCost 等資訊，可以從 `https://api.wpsite.pro/websites` API 取得
>
> 2. cloud.luke.cafe 收到後
> 會依照 API 帶過來的 partner_id ，對該 partner_id 經銷商 扣點以及寫入 log
>
> ## 注意事項
> cloud.luke.cafe 的主要扣點邏輯是寫在 power-partner-server 這個外掛，開發目錄在 `C:\Users\User\LocalSites\turbo\app\public\wp-content\plugins\power-partner-server` 你可以同時修改 `power-partner` & `power-partner-server` 兩個外掛，`power-partner` 負責發送新架構的網站資料，`power-partner-server` 負責處理扣點邏輯還有 log

## 訪談中經程式碼驗證的事實（非推測）

- **根因**：`power-partner-server` 的 `Utils\WPCD::get_app_ids()` 是寫死的 SQL，只撈 `post_type='wpcd_app' AND app_type='wordpress-app'`。新架構站在 api.wpsite.pro，cloud.luke.cafe 無對應 `wpcd_app` post，因此完全不進 `Partner::deduct_sites_points()` 的計費迴圈。使用者陳述屬實。
- **新舊架構不會重複扣點**：兩邊站集合天然互斥（本地 `wpcd_app` post vs PowerCloud UUID 站），無需額外防護。
- **時序衝突**：`Partner::can_cron()` 有「同一經銷商 6 小時內不重複扣點」守衛，查 log 表 `type='cron'` 最後一筆。既有 cron 在 16:30 UTC（UTC+8 00:30），新架構推送在 UTC+8 05:00（21:00 UTC），相距僅 4.5 小時 < 6 小時 → 若共用同一條路徑會被靜默擋掉。
- **`/websites` 前端已在用**：`js/src/pages/AdminApp/Dashboard/SiteList/types.ts` 已定義完整型別，`domain` / `status` / `dailyCost` / `userId` 確定存在。status 實際值為 `creating` / `running` / `stopped` / `deleting`。
- **`cloud_user_id` 在 power-partner 完全不存在**：PowerCloud 登入 `POST /auth/api-key` 只回 `{apiKey}`，未持久化任何 user id。
- **認證現況**：`Utils\Base::set_api_auth()` 對所有經銷商站發同一組 Basic Auth 帳密，接收端靠 body 的 `partner_id` 辨識身分（同 `v2/disable-site`）。
- **接收端無法停用新架構站**：`Partner::disable_sites_by_user()` 走 `do_action('wpcd_wordpress-app_do_toggle_site_status')`，只能停本地 WPCD 站。

## Q&A

- Q: 新架構扣點要不要共用既有的每日扣點路徑？（矛盾：6 小時守衛會讓新架構扣點靜默失效） → A: A — 獨立扣點路徑 + 獨立 log type（`cron_powercloud`），不共用 6 小時守衛，改用每日冪等鍵。理由：不動已穩定的舊 WPCD 流程、帳目可獨立稽核、blast radius 最小。已接受的 trade-off：兩條計費軌道各自維護。**須在 .feature 寫成明確驗收情境**，避免日後重構把兩條路徑併回去而靜默失效。
- Q: `cloud_user_id` 從哪取得？ → A: A — 從 `/websites` 回應取 `userId`（取第一筆），無站台時跳過推送。使用者確認：帶經銷商 API key 打 `/websites` **只回該 key 所屬帳號自己的站**，故回應全量即為計費集合，不需二次過濾。須補防禦性情境：回應中出現多個相異 `userId` 時視為異常（不扣點、寫告警 log），不得靜默取第一筆。
- Q: `dailyCost` 送過去後要不要再套經銷商等級折扣？ → A: A（使用者裁決）— 直接採用 `dailyCost`，**不再**套等級折扣。理由：`dailyCost` 已是 PowerCloud 對該站算出的最終金額，再乘折扣等於雙重打折。此決策使新舊架構定價權威不同（舊：接收端算；新：發送端帶），須在 specs 明確記錄此不對稱，避免後人誤判為 bug。
- Q: 哪些 `status` 的站要計費？ → A: A（使用者裁決）— 只有 `status = running` 計費；`creating` / `stopped` / `deleting` 一律不計費，與舊架構「停用不計費」語義一致。
- Q: 重複推送要怎麼防止重複扣點？ → A: A — 以 `partner_id + 業務日期(UTC+8)` 為冪等鍵；同日重複推送回 200 但不重扣，回應標明 `already_deducted`。冪等實作須對齊 `Log::get_logs()` 既有的 `row_lock => true` 並發鎖，**不可用 check-then-act**（同時收到兩個推送會雙雙通過檢查而重複扣點）。
- Q: 新 endpoint 的認證方式？ → A: **A + 強制 TOFU 綁定**（team-lead 駁回純 A）。基底沿用 Basic Auth + body 帶 `partner_id`，但**必須**加一層 Trust On First Use：首次收到某 `partner_id` 的推送時將 `cloud_user_id` 寫入該用戶 meta 作為綁定值，後續每次比對，不符則拒絕扣點（403）+ error log + 通知管理員；換綁由管理員手動清除 meta。
  - **我原本「偽造者無法得利」的論證被駁回，且駁得對**：真實攻擊動機存在 —— 填入競爭對手的 `partner_id` 狂發推送 → 扣光對手點數 → 連續負數達 7 天 → 對手服務自動停用 → 客戶全斷線，攻擊者從對手掉線中得利。扣點涉及金錢與服務中斷，不能只靠共用帳密。
  - `cloud_user_id` 是 PowerCloud 的不公開 UUID，`partner_id` 只是可猜的 WP user_id；加上這層後攻擊者須同時知道兩者。成本僅一個 meta 加一次比對，遠低於金鑰註冊流程，且該 meta 對帳與 debug 亦可用。
- Q: 推送失敗的重試策略？ → A: A — ActionScheduler 重試最多 3 次、間隔 30 分鐘；仍失敗則寄信給站台 `admin_email` + 寫 error log。3 次 × 30 分鐘最晚於 UTC+8 06:30 完成，仍在同一業務日內，不污染冪等鍵。
- Q: 點數不足時新架構站要怎麼處理？ → A: A（**使用者已裁決，確定值**）— 本期只扣點 + 寫 log，不自動停用新架構站；低點數/停用通知信的「每日扣點、網站數」改為新舊合計。使用者已知悉並接受的 trade-off：欠費經銷商的新架構站會繼續運行，站長仍須持續向 PowerCloud 支付這些站的成本。技術限制：接收端 `Partner::disable_sites_by_user()` 走 `do_action('wpcd_wordpress-app_do_toggle_site_status')`，只能停本地 WPCD 站，無 PowerCloud 憑證故無法直接停 api.wpsite.pro 的站；要停必須反向由經銷商站執行，屬新的雙向協定 —— 明確列為本期範圍外，建議獨立成後續需求（可預留 hook 位置，本期不實作）。
- Q: 扣點 log 的粒度？ → A: A — 一個經銷商一天一筆 log，`title` 內含各站明細 JSON，`point_changed` 為當日總扣點。對齊既有 `deduct_points_with_transaction()` 的做法，且後台點數紀錄表格是「一列 = 一筆交易」。
- Q: 業務日期由誰決定？ → A: **A + 接收端須驗證**（team-lead 補強）。發送端在 payload 帶 `billing_date`（UTC+8 `YYYY-MM-DD`），業務日在發送端一次決定、重試時沿用不重算，避免排程延遲跨午夜導致歸屬漂移。但接收端**不得無條件信任**該欄位 —— 它同時是冪等鍵，可被偽造或因發送端時區設定錯誤而失準。驗證項目：格式須為 `YYYY-MM-DD`（否則 400）、不得為未來日期（以接收端 UTC+8 當日為準，允許 +1 天容差吸收時區邊界）、不得早於當日 7 天以上（防補扣舊帳）；違反時拒絕、寫 error log、不扣點。缺這層的話，發送端每天傳不同的隨機值即可繞過冪等鍵重複扣點。
- Q: `consecutive_negative_days` 要由哪條路徑更新？（Q1=A 衍生的新矛盾） → A: A — 新架構路徑不碰計數器、不觸發停用、不寄低點數通知，一律由既有 00:30 cron 統一判定。該計數器是停用門檻的唯一依據，兩條路徑都遞增會讓 7 天門檻實際變成 3.5 天、經銷商提早被停用。既有 cron 讀的是當下餘額，本就已含前一日新架構扣掉的數，判定自然準確。
  - team-lead 補驗的前提（我原本沒驗）：若 00:30 cron 只遍歷「有 WPCD 站的 user」，純新架構經銷商就永遠不會被判定，A 即為錯。**驗證結果 A 安全**：`Cron::deduct_all_partners_sites_points()` 用 `Point::get_user_ids_by_partner_lvs([1,2])` 遍歷全體 LV1/LV2、與持站數無關；且 `deduct_points_with_transaction()` 唯一提早 return 是 `if (!$this->can_cron)`，無「0 站跳過」分支，扣 0 點仍走到負數判定。
  - **殘留假設須寫成驗收情境**：扣 0 點時 `$this->updated_point` 是否確實等於當前餘額（而非 null/false）。若 `update_user_points()` 在 points=0 時提早返回或回非餘額值，負數判定會失準，純新架構經銷商的負數天數永遠不會累加。情境：「經銷商只有新架構站、無 WPCD 站、餘額為負」。
- Q: （Q8-A 衍生）`is_high_volume_partner()` 的扣點量要不要納入新架構？ → A: **納入**（team-lead 裁定）。該判定區分一般經銷商（7 天停用門檻）與大型經銷商（30 天門檻 + 管理員人工聯繫）。若只算 WPCD 扣點，純新架構的大型經銷商每日扣點量會被算成接近 0 → 不被認定為大型經銷商 → **第 7 天就自動停用**而非享有 30 天緩衝，對規模最大的客戶造成最嚴重誤傷。「這個經銷商規模多大」與通知信是同一個問題，不可有兩套口徑。連帶需修改 `collect_low_points_notice()`（網站數/每日扣點合計）與 `notify_admin_high_volume_negative_partners()`（顯示數字與判定口徑一致）。
- Q: （實作衍生）既有 cron 要從哪裡取得新架構的扣點量與站數來合計？ → A: 推送處理時同步寫入 user meta（金額、站數、對應 billing_date），既有 cron 讀 meta。**刻意不從點數紀錄的 title 反解** —— 解析字串脆弱且與 log 格式耦合。過期處理採 fail-safe：連續數日推送失敗時**沿用最後一次成功推送的值、不歸零**（沿用會讓大型經銷商繼續享有 30 天緩衝；歸零則會使其掉回 7 天門檻而遭提前停用），超過 2 天未更新寫 warning log 供人工檢視。

## 訪談後追加驗證（由 team-lead 獨立複核，已併入規格）

- **6 小時守衛只在 production 生效**：`Partner::can_cron()` 開頭有 `if ('production' !== wp_get_environment_type()) return true;`。故若兩條路徑合併，本地/staging 測起來全綠、上 production 後每天靜默漏帳，且擋下時只寫 warning log、不拋例外。這是**整合測試永遠測不出來**的失效模式，構成 Q1-A 的主論證，並要求一條明確模擬 production 環境的驗收情境。
- **log type 隔離是必要條件而非偏好**：既有守衛查的是 `Log::CRON`（值 `'cron'`）。新架構必須寫不同的 type，需在 `Utils\Log` 新增 `CRON_POWERCLOUD = 'cron_powercloud'`（現有僅 `PURCHASE`/`MODIFY`/`CRON`）。
- **`can_cron()` 的時間算式正確，不得列為缺陷**：`time() > ( strtotime($date) - 2*60*60 )`。紀錄的 date 存 UTC+8 字串，`strtotime()` 以 UTC 解析後比真實時刻晚 8 小時，故「真實 + 6h」等價於「`strtotime(date) - 2h`」。算式與變數命名皆正確，寫入規格時已加註「勿改」。
